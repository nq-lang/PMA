# Options Strategy Payoff Terminal

> **⚠️ SIMULATION & EDUCATION TOOL — NOT FINANCIAL ADVICE, NOT LIVE DATA.**
> Every price, quote, Greek, and "flow" row in this app is generated by a
> seeded local simulator (`engine/market_sim.py`). There is **no brokerage
> connectivity, no order routing, and no real market data feed** of any
> kind. All pricing/Greek/breakeven/probability math is real, textbook
> Black-Scholes-Merton math — computed on top of fabricated inputs.
> Nothing in this tool should be used to make real trading decisions.

A desktop-grade, Python-only options strategy payoff visualizer, inspired
by the *category* of Robinhood-style strategy builders and dark "flow
terminal" tools — original palette, original copy, no vendor branding or
copied assets.

---

## Quick start

```bash
pip install -r requirements.txt
python app.py
```

This opens a native desktop window (via NiceGUI's `native=True` / a
`pywebview` shell — no browser chrome or URL bar). If native mode isn't
available on your platform (some Linux setups are missing GTK/webview
system packages), run:

```bash
python app.py --web
```

which serves the identical UI at `http://localhost:8080` in your regular
browser instead. Functionally identical either way — this is exactly how
this build was verified in its development sandbox (see **How this was
verified**, below), since that environment had no display for a native
window but could reach the web-mode server.

## Why NiceGUI (Tech Stack §2, Option A)

NiceGUI was chosen over the Flask/FastAPI + pywebview + hand-rolled-JS
route (Option B) because:

- It's Python-native end-to-end — no separate JS build step, no REST/WS
  boundary to keep in sync with the engine.
- `ui.echart` gives direct access to Apache ECharts' gradient fills,
  `markLine` annotations, and native hover tooltips/crosshairs — exactly
  what the payoff chart needs — without writing any JavaScript by hand.
- Reactive Python callbacks (`on_change=`) make wiring sliders/dropdowns
  to the engine straightforward and keep 100% of the business logic in
  Python, satisfying §2's requirement.
- `ui.run(native=True)` gives the smooth, GPU-composited, non-Tk/Qt look
  the spec asks for, backed by a real local web server under the hood.

## Architecture

```

├── app.py                    # entry point — launches the NiceGUI window/server
├── engine/                   # pure Python + numpy/scipy — no UI code, fully unit-tested
│   ├── pricing.py            # Black-Scholes-Merton price + all 5 analytic Greeks
│   ├── market_sim.py         # seeded, deterministic MarketSimulator
│   ├── strategies.py         # strategy name -> leg-set factory (full §4 library)
│   ├── payoff.py             # payoff arrays, breakevens, Max P/L, POP, position Greeks
│   └── views.py              # alternate chart views (P/L %, value, % max risk, Greek curves) + Profit Index
├── ui/
│   ├── theme.py               # original dark palette + CSS tokens
│   ├── insights.py            # original hover-tooltip copy (§7)
│   ├── components.py          # stat tiles, leg chips, snapshot header, flow rows
│   ├── chart.py                # ECharts payoff-chart option builder (crosshair + breakeven tooltips)
│   ├── ruler.py                # draggable strike ruler (HTML + tiny JS drag handler)
│   ├── profit_table.py         # price x date heat-mapped grid
│   └── layout.py                # wires everything into the full page + AppState
├── tests/                     # pytest — 152 tests, engine + chart + table logic
├── scripts/                    # dev verification tools (see below) — not required to run the app
├── requirements.txt / pyproject.toml
└── PROGRESS.md                 # full build log: every stage, every bug found & fixed, every design decision
```

`engine/` has zero NiceGUI/UI imports — it's a standalone quant library
you could reuse in a CLI or notebook. `ui/` never does its own math; it
always calls into `engine/` and displays the result, so the chart, the
stats bar, and the profit table are mathematically guaranteed to agree
(this is asserted directly in tests, not just true by convention — e.g.
`test_profit_table_cells_match_asof_payoff_directly`).

## Greek unit conventions (stated once here, and in `engine/pricing.py`'s docstring)

All Greeks are computed **per-share** in `pricing.py`, then scaled to
**per-position** in `payoff.py` by multiplying by the **100-share
contract multiplier**, then by `quantity * direction` per leg, summed
across legs. Concretely, per-share conventions:

| Greek | Convention |
|---|---|
| **Delta** | Dimensionless, in `[-1, 1]`. Raw BSM value, unscaled. |
| **Gamma** | `d(Delta)/dS`, per $1 move in the underlying. Raw BSM value. |
| **Vega**  | **Per 1 percentage point (1 vol-point) IV move** — i.e. textbook per-unit vega × 0.01. A position "Vega 91.77" gains ~$91.77 if IV moves from 63.5% to 64.5%. |
| **Theta** | **Per calendar day** — i.e. textbook per-year theta ÷ 365. Negative for net-long premium, positive for net-short. |
| **Rho**   | **Per 1 percentage point (100bps) rate move** — textbook per-unit rho × 0.01. |

**Stock legs** contribute `Delta = ±quantity × 100` (i.e., `Leg.quantity`
for a stock leg is interpreted as **100-share lots**, the same lot size as
an option contract — this keeps a covered call's stock delta directly
comparable to its short call's delta contribution) and **zero** to every
other Greek.

This two-step (per-share → per-position) scaling is deliberate and kept
explicit in code comments specifically so unit bugs are easy to audit —
see the extended docstring in `engine/pricing.py` for the full reasoning.

## Probability of Profit — model assumption

POP assumes the terminal underlying price is **lognormally distributed**,
i.e. `ln(S_T / S_0) ~ Normal((r − 0.5σ²)T, σ²T)`, calibrated to the
position's current simulated spot/IV/DTE — a standard risk-neutral-ish
assumption, **not a guarantee**. Real-world terminal price distributions
can differ meaningfully (fat tails, skew, jumps, regime changes). This
caveat is also surfaced directly in the Probability of Profit tile's
hover tooltip in the app itself (`ui/insights.py::probability_of_profit_tooltip`),
per spec §7.

## Max Profit / Max Loss — unbounded detection (a design decision worth flagging)

The spec asks whether P/L trends to ±∞ as price → 0 or → ∞. We treat
**these two directions asymmetrically, on purpose**: the underlying price
is physically bounded below by zero, so a long put or short stock's
worst/best case *at* `S=0` is always a **large-but-finite** number (e.g.,
`strike × 100 − premium`), never reported as "Infinity" — this matches
how every real trading platform displays it. Only the `S → ∞` side can
produce a genuinely unbounded result. `engine/payoff.py::max_profit_loss`
computes the exact `S=0` payoff value analytically (independent of
whatever price range the chart happens to be zoomed to) and only flags
"Unlimited" based on the net asymptotic slope as `S → ∞`. This is
documented at length in that function's docstring, and both directions
are covered by dedicated regression tests (`test_long_put_max_profit_
bounded_by_strike_going_to_zero`, `test_long_stock_unbounded_profit_
bounded_loss`) that deliberately use a *zoomed-in* price grid not
reaching `S=0`, to prove the fix doesn't depend on the visible window.

## How this was verified

This project was built and tested inside a sandboxed environment with no
display server. Rather than ship UI code that only "looks right" on
review, verification was done in layers, each one strictly stronger than
the last:

1. **152 `pytest` tests** (`tests/`) — BSM price vs. a Hull textbook
   reference value, put-call parity (scalar and vectorized across a
   401-point grid), all 5 Greeks cross-checked against finite differences,
   breakeven correctness against closed-form vertical-spread formulas,
   bounded (iron condor) and unbounded (long/short call) Max P/L cases,
   POP sanity bounds, and profit-table-cell-vs-engine equality.
2. **A real, running NiceGUI server**, launched inside the sandbox and
   queried with `curl` to confirm the full page renders with zero server
   errors and correct computed values in the DOM.
3. **Real Playwright + Chromium screenshots** of the live app (not a
   hand-built mockup) — this is how two real bugs were caught and fixed
   that neither the test suite nor code review alone would have found:
   an ECharts JS-callback serialization bug (labels rendering as literal
   source text instead of executing), and a systemic event-wiring bug
   where several controls were bound via a raw Quasar DOM event name
   instead of NiceGUI's documented `on_change=` parameter — meaning the
   strategy dropdown silently did nothing until this was found and fixed.
4. **Scripted Playwright interaction tests** (`scripts/`, kept in this
   repo as dev tools, not required to run the app) that actually click
   through the UI — switching strategies, dragging sliders, adding legs,
   changing ticker, and a full Save → switch-strategy → Load round-trip —
   and assert on the resulting DOM state, not just a static screenshot.

The full, chronological build log — including the exact bugs found, the
reasoning behind each fix, and an honest section-by-section pass against
this project's original acceptance criteria — is in **`PROGRESS.md`** at
the repo root. It's intentionally left in the deliverable for
transparency.

`scripts/full_check.py` (real-mouse suite, 12 checks), `scripts/capture_screenshot.py`,
`scripts/interactivity_check.py`, and `scripts/save_load_check.py` are the exact tools used above; they launch
`app.py` as a subprocess and drive it with Playwright. They require
`playwright` (already in `requirements.txt`) plus `playwright install
chromium` once, and are safe to re-run at any time as a regression check.

## Interaction model (why sliders don't break mid-drag)

Interactive controls (ticker, strategy, DTE, expiration presets, view tabs,
the three sliders, rate overrides) are created **once** and never rebuilt.
`refresh()` updates the ECharts instance in place and rebuilds only
display-only regions. An earlier version rebuilt the whole control panel on
every change, which passes a keyboard-driven test but breaks a real mouse
drag; `scripts/full_check.py` now drags sliders and the ruler with real
mouse events to prevent that regression.

## Features beyond the basic payoff chart

- **View tabs**: Profit/Loss $, P/L %, Contract Value, % of Max Risk, and
  Delta / Gamma / Theta / Vega / Rho curves (definitions in `engine/views.py`).
- **Strike ruler**: drag a leg chip to re-strike it (snaps to the strike
  increment); the **expiration row** re-times all legs while keeping strikes.
- **Leg editing**: click a chip to edit direction, quantity, strike, DTE;
  each leg shows its entry premium.
- **Crosshair tooltip**: price, P/L in $ and % of entry cost, position Greeks,
  and which Greek dominates there. **Breakeven markers** explain themselves on hover.
- **Profit Index** = expected P/L / amount at risk under the same lognormal
  model as POP (definition is this project's; see `engine/views.py`).
- **Advanced**: override the simulated risk-free rate and dividend yield.

## Known limitations / honest gaps

- **Native-window rendering** (vs `--web`) was not visually verified: the
  build sandbox had no display for `pywebview`. The UI code is identical in
  both modes, but this is unconfirmed rather than assumed away.
- **Stat-tile hover tooltips** render with a lighter background than the
  intended dark theme in the test browser (cosmetic; content is correct).
- **Ruler** drags strikes only; stock legs have no ruler chip (edit them
  via the Positions panel). Chips at nearby strikes stack onto extra rows.
- Only some of the 32 strategies were switched live in a browser (Bull Call
  Spread, Iron Condor, Long Straddle, Custom-via-quick-add); all 32 are
  covered by the automated strategy/payoff tests.
- Profit Index and the P/L %, % of Max Risk view definitions are documented
  choices, not industry standards; other platforms may define them differently.

## Explicit non-goals (per spec §9, reiterated)

No real brokerage or market-data integration of any kind. No storage of
real financial account numbers, positions, or credentials. No reproduction
of any vendor's copyrighted UI assets, icons, logos, or exact brand color
values. No investment-advice language anywhere in the UI — every output is
framed as educational/simulated.

## Running in GitHub Codespaces / VS Code Dev Containers
Opening the repo in a Codespace builds the container (`.devcontainer/devcontainer.json`), installs
`requirements.txt`, and on attach runs `scripts/start_server.sh`, which starts the web server in the
background on port **8080** (auto-forwarded and opened in VS Code's preview). Pages: `/` options
payoff, `/futures` futures payoff & risk. Restart any time with
`bash options_payoff_terminal/scripts/start_server.sh`; log at `/tmp/pma-server.log`.
Headless environments (Codespaces, containers, no `$DISPLAY`) automatically use browser mode; set `PORT` to change the port.
